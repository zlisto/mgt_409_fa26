A venue FAQ is a SELECT, not a vector store

  • HW4 Problem 2: invent ≥4 categories, SELECT those rows, then answer.
  • Do not embed the FAQ. Do not stuff the whole policy into every prompt.
  • One customer-service brain. Conflicting agents on one venue policy start a turf war.

If the bot invents lockers or an elevator, you stuffed the model instead of selected FAQ rows.

Passwords are not a prompt

Fail

password = "hunter2" in JSON. Printed in the terminal. Logged in chat history.

Pass

Salt + hash in SQLite (PBKDF2 settings live in meta). Compare hashes. Never echo what they typed. Signup = new salt.

If the users table is plaintext, you do not have a web app. You have a leak with CSS.

Chats that survive a refresh

  • POST /chat writes both sides of the turn into SQLite.
  • GET /chats is that user’s threads only.
  • “New chat” starts a row. Old threads stay. That is the product.

If the thread dies on refresh, you returned JSON and never INSERTed.

What to remember

  • A web app is UI + API + database, not a nicer print statement.
  • Hash passwords. Persist chats. Ground answers in SELECTed rows.
  • Prompt-to-app tools make this cheaper to start — and easier to ship a demo that lies.
