In-class goal: Leave with a React (Vite) page talking to FastAPI, with FAQ and chats in SQLite — the shape of Homework 4, not the assignment. Do not use the HW4 zip. Do not deploy (Lecture 8). Invent a 6-row fake venue FAQ.

If it only works in the terminal, you built a lab. If a classmate can click it, you built an app. A public URL is next week.

Step 1 Two folders, SQLite seed 0–5 min

Empty project. Not College Street Music Hall data — a toy so you learn the wiring. SQLite is the source of truth from minute one.

Create lec07_web/backend/ and lec07_web/frontend/.
In backend/, write seed_db.py that creates venue.db with tables:
  faq(id, category, question, answer)
  users(id, username, salt, password_hash)
  messages(id, username, role, text, created_at)
Insert 6 FAQ rows (bag policy, door time, refunds, no elevator, food, tickets).
Do not store a plaintext password. README: backend is FastAPI on 8000, frontend is Vite on 5173, database is venue.db.
Do not copy Homework 4 files. Do not add a Render/Dockerfile.
Check: sqlite3 venue.db "SELECT category, question FROM faq;" prints 6 rows. README names both ports.

Step 2 FastAPI: health + chat from SQLite 5–14 min

The browser never holds the API key. Chat reads FAQ rows with SQL — do not embed, do not dump the whole table into every prompt.

In backend/server.py make a FastAPI app with CORS for http://127.0.0.1:5173.
GET /health → {"ok": true}.
POST /chat JSON {message} SELECTs matching faq rows from venue.db (by category or keyword), asks the OpenAI API to answer only from those rows, returns {answer, refused, citations}.
Never invent an elevator. Keys load from .env on the server only.
Run: uvicorn server:app --host 127.0.0.1 --port 8000
Check: curl http://127.0.0.1:8000/health works. POST {"message":"Is there an elevator?"} returns refused true or an answer that cites the no-elevator row.

Step 3 Vite React chat UI 14–24 min

A real frontend folder, not index.html sitting next to Python. Stay on localhost — no deploy.

In frontend/ scaffold React + Vite. One CSS file (not only inline). Dark venue colors, big type.
A text box + Send that POSTs to http://127.0.0.1:8000/chat and shows answer + refused.
README: npm install && npm run dev. Document whether you use a Vite proxy or the full URL.
Do not put OPENAI_API_KEY in any frontend file or VITE_ variable.
Check: From the browser you can ask about bags and see a reply without opening a terminal for that turn. FastAPI is still on 8000; Vite is on 5173.

Step 4 Hash a password, persist the thread 24–34 min

HW4 uses PBKDF2 in SQLite. In class, prove two product rules: never store plaintext, and chats survive refresh.

Add backend/auth.py with hash_password(password, salt) and verify().
Seed one user in venue.db (salt + hash only).
POST /login {username, password} → {ok, token}. Never log or echo the password.
POST /chat also INSERTs both the user message and the assistant reply into messages.
GET /chats?username=... returns that user's turns from SQLite.
Frontend: a login field that must succeed before chat is enabled. After a browser refresh, prior turns reappear from GET /chats.
Check: Wrong password → ok false. Right password unlocks chat. SELECT username, password_hash FROM users; has no plaintext. Refresh the page: the last turn is still there.

Step 5 AI_prompts.md 34–40 min

Same habit as homework: log what you asked the vibe coder, in your words. If you still have minutes, screenshot is stretch — not required to “finish” class.

Create AI_prompts.md with a Lecture 7 section. One prompt summary per step above.
Note what broke (CORS, ports, hash mismatch, chats vanishing) and the follow-up prompt that fixed it.
Check: Five step headings; at least one “what was lacking” sentence.

Stretch (if time): Screenshot button that captures the current page (not the webcam) and POSTs it with the message. Backend uses vision + the FAQ rows. Typed chat must still work if the button fails. Do not deploy.
