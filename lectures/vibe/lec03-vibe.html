Lecture 3: Tool Use

← Slides All lectures · 40 minutes in class

In-class goal: Ship a real search_web tool that returns titled URLs, let an LLM invent queries from a tiny ICP JSON, save search_results.json, then run a function-calling variant where the model requests the tool. This is the Homework 2 search wrench—not the FiftyFlowers answers, not the email sender, not the agent loop (that’s Lecture 4).
40-minute clock
  1. 0:00–6:00 — Scaffold lec03/
  2. 6:00–14:00 — Implement search_web + CLI
  3. 14:00–20:00 — Query prompt from the ICP
  4. 20:00–30:00 — run_search.py (HW2 Problem 3 shape)
  5. 30:00–37:00 — Function-calling variant
  6. 37:00–40:00 — Log prompts + click two URLs

If you are behind at 30:00, skip README polish and still do the function-calling step. Stretch (cap at 3 calls in code) is optional.

Toy company in class: Petal Depot, a bulk flower wholesaler. Same shape as HW2. Different site, so you cannot paste this session in as the homework zip.

Vibe this from scratch (prompts in files, outputs in a folder, .env gitignored). Use OpenAI via Portkey the way the course already set up.

Step 1 Scaffold lec03 0:00–6:00

Separate the search function from the “invent queries + save JSON” script. Secrets stay in .env.

Create a folder lec03/ with:
- search_web.py
- run_search.py
- prompts/search_queries.md
- fixtures/icp.json (tiny fake ICP for "Petal Depot", a bulk flower wholesaler targeting wedding planners and floral studios; include disqualifiers for one-off retail brides)
- fixtures/search_results.stub.json (5 fake but well-formed hits with https URLs, for offline mode)
- output/
- requirements.txt (openai, python-dotenv)
- .env.example with OPENAI_API_KEY=
- .gitignore ignoring .env and output/*
- README: how to run; note that search_web may use OpenAI Responses web_search OR the stub if no key / flag --offline
No real API keys in any file.
Check: Folder exists; README explains live search vs stub; no secrets in tracked files.

Step 2 Implement search_web(query) 6:00–14:00

The tool returns evidence, not a vibe paragraph. Every hit needs a URL the grader could click.

In search_web.py define:

search_web(query: str, max_results: int = 5) -> list[dict]

Each dict keys: title, url, snippet.
- Prefer OpenAI Responses API with tools=[{"type":"web_search"}] when OPENAI_API_KEY is set.
- If --offline or no key, filter fixtures/search_results.stub.json by query substring.
- Drop any hit missing a https URL.
- Truncate snippets to 280 chars in Python (do not dump whole pages into the model).
Add a CLI: python search_web.py "austin wedding planner" that pretty-prints JSON.
Check: Running the CLI prints ≤5 objects; first object has a real-looking https url key. Offline mode still returns URLs from the stub.

Step 3 Prompt: invent search queries from an ICP 14:00–20:00

Homework 2 will have the model propose ≥5 queries from icp.json. Practice that contract now.

In prompts/search_queries.md tell the model:
Input: ICP JSON for a bulk flower wholesaler.
Output: JSON only, {"queries": [string, ...]} with at least 5 distinct web search strings.
Rules:
- Queries should find BUSINESS customers (planners, studios, venues), not "buy roses cheap".
- Include city or region in some queries.
- Do not name invented companies.
- Do not include personal social-media hunting language.
Check: Prompt file states the JSON shape, the ≥5 rule, and “business customers not retail shoppers.”

Step 4 run_search.py — queries then tool 20:00–30:00

Still a script, not an agent loop. You decide the order: LLM queries → your code searches each one. HW2 Problem 3 puts this shape in one script named search_web.py; today we keep the function separate so the handshake is obvious.

Create run_search.py that:
1. Loads fixtures/icp.json
2. Calls gpt-4o-mini (or the Portkey model we use in class) with prompts/search_queries.md + the ICP, response_format json_object
3. Parses queries (require len >= 5)
4. For each query, calls search_web(query)
5. Writes output/search_results.json as:
   {"queries": [...], "results": [{"query","title","url","snippet"}, ...]}
6. Prints token usage and number of hits.
CLI: python run_search.py --icp fixtures/icp.json --out-dir output
Refuse to write results that lack urls. If a query returns nothing, continue.
Check: File exists; ≥5 queries; every result row has query + url.

Step 5 Function-calling variant 30:00–37:00

Same destination, tool-native path: the model requests search_web instead of you always calling it first. Max turns are a cap, not an agent loop (Lecture 4).

Add research_with_tools.py that:
- Registers search_web as an OpenAI function tool (name search_web, parameters {query: string, max_results: integer})
- System prompt: propose queries from the Petal Depot ICP, call search_web up to 3 times, then stop.
- Your code executes each tool call and appends results.
- Max 4 model turns. Then write output/tool_trace.json with the tool call names/args and output/search_results.json in the same schema as Step 4.
- Print a warning if the model tries to call anything other than search_web.
Check: Logs show at least one search_web tool call; final JSON still has https URLs.

Stretch (if time): Cap total search calls at 3 in code even if the model begs for more. That’s a manager control, not a prompt hope.

Step 6 Log prompts + click two URLs 37:00–40:00

Course habit: what you typed to the vibe coder, in your words. Then prove the tool, not the JSON.

Append a Lecture 3 section to AI_prompts.md summarizing, in my own words: scaffold, search_web implementation, query-prompt design, run_search.py, and the function-calling variant. One sentence on what broke on the first try if anything did.
Check: Lecture 3 section exists with ≥4 bullets. No API keys pasted into the log. Open two saved URLs in a browser. If they 404, fix the tool—not the JSON by hand.
